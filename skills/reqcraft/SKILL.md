# ReqCraft

把需求转成业务场景、规则和可观察的验收结果。适用于同一人负责前端、后端和验收的工作方式，无需模拟多角色审批。

## 入口

| 动作 | 交付物 |
|---|---|
| `reqcraft-analyze` / `analyze` | 场景、规则、状态转换和待确认问题。见 [需求分析](references/workflow-analyze.md) |
| `reqcraft-spec` / `spec` | Given–When–Then、验收责任、验证层次和就绪状态。见 [验收规格](references/workflow-spec.md) |
| `reqcraft-audit` / `audit` | 规格缺口、静态实现线索与已有验证证据。见 [验收审计](references/workflow-audit.md) |
| `reqcraft-help` / `help` | [用法与范围](references/help.md)。只读技能资料 |

按用户意图选择动作。“处理这份 PRD”默认走 `spec`。先补齐生成规格所需的分析，已有分析可直接复用。审计以当前规格为准，缺少规格时报告该缺口。

## 共用规则

- 需求和用户已确认的决策用于判断预期。源码用于定位现有行为。两者不一致时列出冲突及位置，业务选择交给需求方。
- 区分 `PRD 已明确`、`用户已确认`、`仓库事实`、`建议待确认` 和 `缺失待确认`。引用章节、路径、符号或已有报告位置。资料不可用时注明影响范围。
- 按业务风险检查异常、权限、状态冲突、重复和并发。没有依据的行为作为待确认项，避免补造角色、阈值、接口、字段和错误码。优先询问阻塞判断的事项，其余部分可继续。
- 使用稳定的 `SC-01`、`BR-01`、`AC-01`、`Q-01`。修订时保留原编号，标明修改、废弃和受影响的关联项。待定业务决策交给需求方，已确认 AC 和工程待定项交给开发，验证层次和证据缺口交给测试。
- 可按需静态读取相关源码、工程约定、接口定义、测试源码和已有运行报告。技能交付止于需求规格和只读审计。业务代码、技术设计、接口实现、测试代码、测试环境、测试执行和缺陷修复由下游任务负责。禁止以构建、运行测试、调用业务接口或改数据代替静态审计。
- 默认在对话交付。只有用户明确要求创建或更新规格文档时才写入目标仓库。优先沿用已有目录，否则使用 `docs/requirements/<feature-slug>.md`。更新前读取现有内容，保留历史决策和证据。明确只读时，审计发现直接在对话交付。

生成或审计规格时参照 [模板](assets/acceptance-spec.template.md) 和 [质量规则](references/quality-rules.md)。如需机械检查模板格式，使用 [本地校验脚本](scripts/check_spec.py)。脚本只读规格文件，业务语义和证据有效性由宿主结合原始资料判断。
