# 验收规格

## 业务 AC

复用已有分析或按 [需求分析](workflow-analyze.md) 提取 `SC` 和 `BR`。为核心场景分配 `AC`，关联相关场景及规则。

- **Given** 给出决定行为的角色、权限、初始状态、数据和依赖。
- **When** 写一个明确的业务动作或事件。
- **Then** 写可观察的业务结果，涵盖必要的状态变化、可读数据、反馈和禁止发生的副作用。
- **状态** 使用「已确认」「草案待确认」或「已废弃」。依赖未决业务规则的条目标为草案，记录对应 `Q`。

一个 AC 对应一个行为目标。同一目标可包含多个相关结果断言。

## 验收责任

仅有 PRD 时，按需记录前端可感知交互、后端权威校验与跨层结果，技术映射标为「未开展」。读取真实仓库后，定位 UI、Controller、Service、鉴权、数据模型和接口约定等相关位置。区分已有工程事实、建议核对点和技术待定项。尚未确定的契约细节作为交接项。

为关键 AC 给出最低充分验证层次和可观察结果。组件、单元、接口、集成和 E2E 按行为选择，关键跨层路径再考虑 E2E。详细步骤、测试数据和代码交给测试任务。

## 就绪判断

- **业务规格**。核心规则与 AC 已明确，且没有阻塞业务结论的 `Q`。
- **技术映射**。依据真实工程确认相关责任和契约，且不存在阻塞开发的技术待定项。

两项独立标记。按 [模板](../assets/acceptance-spec.template.md) 交付并按 [质量规则](quality-rules.md) 核对。保留旧规格中的 ID、历史决策及已有证据。
