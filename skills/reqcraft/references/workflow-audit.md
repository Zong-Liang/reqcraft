# 验收审计

先列明实际可用的 PRD、现有规格、仓库位置和运行报告。默认在对话交付，用户明确要求写入时才在已有规格追加或更新审计记录。

1. **覆盖与一致性**。从范围内的 PRD 条款核对场景和规则，再逐条反查已确认规则对应的 AC。对照规则的适用条件、失败路径和预期结果，判断关联的已确认 AC 合起来覆盖了哪些要求。发现缺口时，在规则名下列出遗漏的条件或结果。若没有关联 AC，或关联的 AC 均为草案、已废弃，注明原因。尚未形成规则的遗漏记在 PRD 条款或场景名下。核对规则冲突、前后端责任冲突，以及待定规则被误标为确认的情况。
2. **可验证性**。核对前提、动作和结果是否具体，能否判定通过或失败。静态格式检查可参考 [校验脚本](scripts-check.md)。
3. **实现线索**。有源码时定位对应逻辑与缺失位置，记录路径及符号。源码和测试文件可说明实现或验证意图，运行结果需独立证据。
4. **已有验证证据**。将报告中的用例与 AC 的前提和预期结果对应起来。依据执行明细，或与该次运行相匹配的测试源码，核实用例实际检查了什么。一个 AC 有多项结果时，分别列出有通过证据、有失败证据和尚缺证据的结果。用例中途失败时，区分已观察到的失败与尚未执行的检查。报告只有用例名和状态、无法核实断言时，保留用例运行状态，将对应业务结果标为「证据不足」。记录报告位置、用例标识及已知的环境、版本和时间，限定旧报告或环境不明的证据适用范围。

复核修订后的 AC 时，对照变更说明或前后两版规格，找出角色、前提、触发条件、预期结果及禁止副作用的实质变化。按变化逐项核对旧报告，保留它在原版本和运行条件下能证明的结果，为新增或改变且缺少对应证据的部分注明缺口。例如，审批角色从管理员扩展到代理人时，仅覆盖管理员的旧报告仍可支持当时的管理员路径，代理人路径需另有证据。仅调整措辞且业务含义相同时，沿用原证据及其适用范围。

问题注明来源位置、受影响的业务行为和交接对象，有关联 AC 时保留其编号。对阻塞验收的发现，在原记录写明可核实的关闭条件：规格缺口可通过已确认且覆盖缺失行为的 AC 关闭，运行证据缺口则需能证明相应结果的报告。复核时记录证据出处；满足条件后标为「已关闭」，部分满足时保留「未关闭」并指出剩余缺口。

结论分别记录规格质量、技术映射、实现线索和验证证据。通过或失败只适用于已核实的业务结果和运行条件。审计期间禁止执行测试。
