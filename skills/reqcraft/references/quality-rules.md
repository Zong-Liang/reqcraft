# 需求与验收标准质量检查

用于审查需求规格，不是测试执行指导书。

## 1. 业务规则质量

- **有来源**：原文明确、用户确认、工程事实和建议推断分开记录。
- **无实现绑架**：优先写业务不变量，而不是指定前端框架、数据库事务、锁等技术方案。
- **具体**：限定参与者、适用条件、允许/禁止的行为和业务结果。
- **可证伪**：相同输入下可以判断满足或违反规则；不得用“正常处理”“合理提示”代替要求。
- **不矛盾**：状态流转、权限与其他规则相容；发现矛盾时不擅自挑选一方。

| 原始描述 | 可验收的业务表达示例 | 必须待确认的内容 |
|---|---|---|
| “提交时进行校验” | “存在必填项缺失时，申请不进入待审批状态” | 必填字段、空值定义 |
| “不能重复提交” | “同一申请在首次成功提交后，不创建第二条审批流程” | 重复请求的期望反馈、并发规则 |
| “无权限不能操作” | “不具备业务授权的请求不能改变申请状态” | 权限角色、数据范围 |
| “保存成功” | “再次打开申请时，可读到已保存字段值” | 字段清单、一致性时点 |

示例只说明如何改写，不能作为 PRD 已确认的规则。

## 2. AC 质量

- Given 包含决定行为的角色、数据、状态与依赖前提。
- When 是一次可识别的动作，必要时区分触发与异步完成。
- Then 验证**业务结果**，包括状态、可读取数据、反馈及禁止副作用。
- 避免“接口返回 200”替代业务正确性；响应结构正确也不代表副作用正确。
- 同一规则不必在多个 AC 重新定义；使用关联的 BR ID。
- 待确认事项不得混入“已确认”的 AC；建议方案必须明确标注建议。
- 仅覆盖与本次需求相关的异常、边界、权限和并发风险，避免机械穷举。

## 3. 前后端责任边界

| 层次 | 主要验收关注点 | 常见误区 |
|---|---|---|
| 前端 | 用户操作、数据展示、错误反馈、加载/空状态、权限可见性 | 以按钮隐藏代替后端授权 |
| 后端 | 权威业务规则、鉴权、状态更新、持久化一致性、重复/并发操作 | 仅断言返回码，忽略业务状态与副作用 |
| 跨层 | 用户完成的完整业务目标、前后端及外部依赖交互结果 | 认为前后端各自通过就代表完整流程通过 |

仅有 PRD 时可描述职责原则；技术实现细节必须来自仓库、明确的工程规范或后续技术决策。

## 4. 审计证据等级

- **需求陈述**：PRD 或用户给出的业务要求；不代表实现。
- **规格覆盖**：存在 SC / BR / AC；不代表代码已实现。
- **实现线索**：静态源码中能定位相关逻辑；不代表运行正确。
- **测试设计/测试文件**：能找到某个 AC 的验证意图；不代表执行成功。
- **运行证据**：现有可核实的执行报告、环境与结果；才可在证据范围内报告通过或失败。

没有运行证据不得写“验收通过”。即使现有报告通过，也要指出报告覆盖的范围，不能扩展成全功能通过。

## 5. 交接规则

- 将不明确的业务决策交回用户确认，不能交给开发 Skill 自行猜测。
- 开发 Skill 接收已确认的 AC 和技术待定项，负责设计与实现；本 Skill 不写业务代码或接口定义。
- 测试 Skill 接收 AC、验证层次建议和覆盖缺口，负责详细用例、测试代码、框架与执行；本 Skill 不产出可执行测试。
- 需求变更时维护 SC / BR / AC 的稳定关联，标记废弃项，提醒开发和测试 Skill 处理受影响的实现及回归范围。
